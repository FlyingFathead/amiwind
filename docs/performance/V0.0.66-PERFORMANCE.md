# v0.0.66 performance: what changes for speed, with the numbers

_Last updated with AmiWind v0.0.66-dev7 (15 November 2026)._

This page lists what v0.0.66 changes for speed, in the game and in the builder. Every number says what measured it and on
what. A figure that has not been measured is marked as such, and is not estimated here. Sections follow the form of the
[builder profile](BUILDER_PROFILE.md) and the [renderer counters](RENDERER-COUNTERS.md).

## In the game

### The prison ship's hold

Measured with a model of the engine's own test (the brush model box against the view, then every face of a model in view
through the back-face test and the edge clipper) from four fixed spots in the hold, eight headings each, on the v0.0.65
release map (PRISON-SHIP-POLY-COLLISION-65). The model reproduces the renderer counters measured in v0.0.57 (the heaviest
heading: 69 models, 22,591 faces tested and 11,475 facing, against 69, 22,416 and 11,491 measured). Details and the
checks: [the weight of the hold](../SHIP_INTERIOR.md#the-weight-of-the-hold).

| Measure | Before | Added | After |
| --- | ---: | ---: | ---: |
| Faces tested per view, average | 14,128 | -3,379 (-24 %) | 10,749 |
| Faces tested, worst view (the start, looking down the hold) | 23,386 | -2,030 (-9 %) | 21,356 |
| Faces facing the camera, average | 7,285 | -1,797 (-25 %) | 5,488 |
| Faces drawn in all | 26,628 | -2,030 (-8 %) | 24,598 |
| Collision clipnodes | 29,182 | -11,128 (-38 %) | 18,054 |
| Steps of a collision point test, average | 837 | -188 (-22 %) | 649 |
| Map file, before the later stages (bytes) | 3,783,692 | -414,116 (-11 %) | 3,369,576 |

Three methods, each behind a builder switch with the old path selectable: the shell's collision bevels exact on the walkable
plates (clipnodes 29,182 to 18,054; a point test 837 to 649 steps), the hammocks' small closed parts drawn as boxes
(26,628 faces drawn to 24,598), and the shell's faces in draw tiles of at most 512 faces (no change in faces; the parts
behind the view are no longer tested). The worst view gains least: it looks at most of the room. The standing-box sweep of
the bevel rule pushes no point through a wall (early stops 1.67 % of the far points against a limit of 2 %), and the
connectivity check reaches the upper deck with every value.

### Area loads: the sound lookups (v0.0.66-dev5)

Since v0.0.66-dev2 the sound loading of an area load took 3.5 to 5.6 times as long for the same sounds, because no name
lookup of a sound fitted the boot partition's 30 file system buffers any more (IMAGE-LOADS-SLOWER-66; the sessions side by
side are on [its page](../bugs/IMAGE-LOADS-SLOWER-66.md)). From v0.0.66-dev5 the image step orders every directory hash
chain busiest first and gives each partition the buffers its longest lookup needs: the boot partition 150, 72 to 73 KiB of
Fast RAM measured, the CHIM world partition 40 ([directory hash chains and disk buffers](../STORAGE.md#directory-hash-chains-and-disk-buffers)).

Header blocks per lookup, measured on the v0.0.66-dev4 boot partition (29,385 files) through the new image step code, no
build and no session (median, longest):

| Lookup | As written (v0.0.66-dev4) | Busiest first (v0.0.66-dev5) |
| --- | --- | --- |
| A sound outside the pool (370 files) | 34, 42; none within 30 buffers | 6, 14; all within 30 |
| A pooled sound (7,086) | 81, 159 | 54, 132 |
| A model or other file under `progs` (13,322) | 113, 169 | 20, 140 |
| Every file (29,385) | 73, 169 | 25, 140 |

The sound loading of three area loads at 32 MB Fast, from the test sessions (the same sounds and bytes on each image):

| Load | v0.0.66-dev1 | v0.0.66-dev2 | v0.0.66-dev5 disk layout |
| --- | ---: | ---: | ---: |
| Seyda Neen: 24 sounds, 244 KB | 139 ms | 480 ms | 59 ms |
| Balmora: 25 sounds, 297 KB | 139 ms | 777 ms | 118 and 147 ms (75 and 76 ms at the start) |
| Vivec: 51 sounds, 641 KB | 306 ms | 1,078 ms | 147 and 165 ms |

The v0.0.66-dev5 column was measured on the v0.0.66-dev6 image, which has the v0.0.66-dev5 disk layout (the game and the
disk are those of dev5), in the test session's area hops and one further session: the sound stage printed with each long
frame of a map load, JIT; two figures stand where the same load ran more than once. The sound stage is below the
v0.0.66-dev1 figure at Seyda Neen (59 against 139 ms) and Vivec (147 and 165 against 306 ms); at Balmora one load is below
(118 ms) and one just above (147 ms) its 139 ms; all three are far below the v0.0.66-dev2 figures. This measures that stage only, not the whole load.

The buffers cost memory. Free Fast RAM after a load, the v0.0.66-dev6 image against the v0.0.66-dev4 image, the same steps
at 32 MB Fast:

| Load | v0.0.66-dev4 | v0.0.66-dev6 | Difference |
| --- | ---: | ---: | ---: |
| Balmora | 2,010 KiB (largest block 1,938) | 1,938 KiB (largest 1,865) | -72 KiB |
| Balmora, the second time | 1,978 KiB | 1,906 KiB | -72 KiB |
| Vivec | 1,396 KiB (largest 1,342) | 1,323 KiB (largest 1,270) | -73 KiB |

The 150 buffers of the boot partition (and 40 of the world partition) take 72 to 73 KiB of Fast RAM, inside the 60 to 75
KiB expected; the program hunk is unchanged. That is about 5 % of the free Fast RAM at Vivec.

The v0.0.66-dev5 build's image step reported the relink on the real image: on the boot partition 86 of 4,559 directory
hash chains relinked and 232 header blocks rewritten, no block moved; the name lookups of its 29,385 files from a median of
73 to 25 header blocks, the longest from 169 to 140, and 16,306 of them within 30 buffers instead of 3,613. The CHIM world
partition was already short (median 7, longest 30) and kept its order. The partition table carries 150 buffers for the
boot partition and 40 for the world partition. The image stage took 908 s against 894 s for v0.0.66-dev4 (about 14 s
more for the relink). The load times in play are above.

## In the builder

### Unit caches keyed by what each unit reads

The builder's unit caches key on what the unit reads ([the build cache](../BUILD_CACHE.md#the-merging-reader-and-the-expansion-layers-v0066-dev1)).
The merging reader and the layered archive reader count as a fixed text naming their output, not as their code, so a reader
edit with the same output re-keys nothing. Measured against the v0.0.66-dev1 build's units (base game), with both
expansions selected: 55 of the 1,769 room residents change, 4 of the 80 player view units, about 3 % of the NPC library's
appearances, and the 935 batched rooms bake again (they read 47 textures the expansion archives replace). The dev1 build,
for the base game alone, baked all 1,769 room residents again (about 7 hours) for a reader change before these keys.

### The reuse check and stored unit groups (v0.0.66-dev6)

Every v0.0.66 snapshot's reuse check stopped the world scenery and world flora stages for the units their caches stored
under earlier keys (2,064 and 1,931 in the v0.0.66-dev5 check), although no region is converted on this line: every
region is a CHIM cell, and the builds took both stages from the earlier build. From v0.0.66-dev6 the check counts only the
regions a stage converts (BUILD-REUSE-STOP-COUNTS-STORED-GROUP-64), covered by tests. The v0.0.66-dev6 check itself still
stopped both stages with the same counts (2,064 and 1,931): its stage plan treats them as stages that run, while the build
takes both from the earlier build, so a second cause is open. Either way the change removes a stop, not a cost: no stage
gets faster.

### Build records

Source: the master builder's result records of 13 November 2026 (wall time, stages reused and rebuilt, the performance
guard), with 24 build workers.

| Build | Wall time | Stages reused / rebuilt (of 48) | Outcome |
| --- | ---: | ---: | --- |
| v0.0.66-dev1, first build, expansions off (commit 40ee26d) | 40,725 s (11 h 19 min), the build 40,402 s | 7 / 41 | stopped in the image step |
| v0.0.66-dev1, resumed (commit 7130bd0, source diff 2 files) | 3,761 s (63 min), the build 3,365 s | 46 / 2 | stages passed; the performance guard failed |
| v0.0.66-dev2, plan only (commit ef8b970, source diff 832 files) | 312 s (the check) | 21 planned reusable / 27 rebuilt, 0 unexpected | no build ran |

- The resumed build took 3,761 s against 40,725 s for the first (-37,000 s, -91 %), by reusing 46 of the 48 stages. This is a
  resume of the same version, so it measures the reuse, not a faster stage.
- The first dev1 build's resource plan expected about 1 h 15 min with the stages added up (it had no measurement for one
  stage), and the build took 11 h 19 min; its plan was made from the stage times of earlier runs, in which the room
  residents were not baked again. The rebuild of every unit for the reader change (BUILD-UNIT-KEYS-REACH-64) is what the
  content keys above remove.
- The dev2 plan is a plan, not a build: it says 21 of 48 stages are reusable against the resumed dev1 run, and its resource
  plan adds the stages up to about 15 h 55 min of wall time for the 27 stages that rebuild (the CHIM stage alone about
  1 h 59 min on 17 workers). The measured time is that of the dev2 build, not yet taken.

### The build start's pre-flight (BUILD-PREFLIGHT-SERIAL-REPEATED-66)

Before its first stage a build checks the owners of every workspace cache entry and works out every stage key; both ran on
one core, three times per build start (the check before the request, the build server's check of the request, the build
itself). A profile of the unchanged check put about 35 % of its time in the cache walk (14.2 million entries, one `lstat`
each) and most of the rest in the stage source analysis. Both now run on a process pool, and the analysis is kept per source
tree ([the build cache](../BUILD_CACHE.md#the-pre-flight-on-every-core-once-per-source-tree)).

Measured on the v0.0.66-dev2 inputs of commit 1cbb84c: the same check command, the same environment switches and the same
reuse source (the v0.0.66-dev1 run), on 8 workers; the after tree is the 1cbb84c source with only this change.
Another check or a starting build ran at the same time, which slows the parts that read the disk (the cache
walk, the game-file check, the reuse plan's file hashes), so the figures carry that load.

| Check | Wall time | Cache owner check | Stage source analysis |
| --- | ---: | --- | --- |
| Before (the builder of 1cbb84c) | 672.6 s | one core (about 7.8 min until the run name) | one core |
| After, the first check of the tree | 153.0 s | 13.4 s on 8 workers | worked out in 9.1 s on 8 workers (48 stage scripts, 590 modules) |
| After, the next check of the same tree | 166.6 s | 27.9 s on 8 workers (beside a starting build) | taken from the first check in 0.7 s |

- Every one of the 43 stages the plan reuses had the same fingerprint before and after, and the reuse preflight said the
  same (43 of 48 planned for reuse, 5 rebuilt, 0 unexpected).
- The next check gains less than the analysis alone suggests: its disk-bound parts ran beside a starting build. What remains
  on one core is the reuse plan's check of every file it would take from each earlier run (SHA-256 on 8 threads) and the
  unit-cache report's keys.

### The performance guard of the resumed dev1 build

The guard failed on one section of the image step, the guard torches: 1,139 s against 336 s in the baseline with the same 6
units (+239 %; 4.53 cores against a baseline of 4.70). It is registered as
IMAGE-GUARD-TORCHES-SLOW-66 in the [bug register](../BUGS.md) and is open: the cause is not found yet. The same record
shows the image step on 10.5 of 24 cores for 1,319 s with units queued.
The size guard passed (nothing grew).
