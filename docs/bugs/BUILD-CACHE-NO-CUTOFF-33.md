## Status: 9 October 2026

Repair in v0.0.33 development (not shipped). Found while measuring BUILD-CACHE-OVERBROAD-33 on the
AmiWind "MiniWind" Playtester Build stage list (version 0.0.33-dev1, run mw-033c, source
v0.0.33-miniwind 76a324f).

## Symptom

From mw-033c to the next MiniWind source (v0.0.33-miniwind-ext 1120d84), the only scene-chain stage
whose own inputs change is `intro` (the startup screen code, `tools/prepare_logo.py`). Every stage
after it in the scene chain (census, balmora, balmora-interiors, harvest, hand-catalog, chim,
door-audio, character, reading, opening-references) is then rebuilt too, whether or not `intro`'s
outputs changed.

## Where

`tools/build_cache.py`: a stage's fingerprint holds the fingerprints of the stages it depends on, and
reuse is planned before any stage runs. A dependency that is rebuilt therefore always rebuilds its
dependents, even when it writes the same bytes as in the old run.

## How it happened

Fingerprints chained through dependencies are the simple, safe rule: the planner cannot know a
rebuilt stage's outputs before it runs.

## Why it was not caught

Reuse was measured as fingerprint changes only; the cost of the chain after one real change was not
looked at until the MiniWind builds.

## Reproduction

Change only `tools/prepare_logo.py` and build with `--reuse-from` a passed MiniWind run: intro and
every stage after it run.

## Repair

Conditional reuse (`tools/build_cache.py`): a stage whose own fingerprint parts (everything but the
fingerprints of the stages it depends on) are unchanged, or whose fingerprint is unchanged but a stage
before it runs again, is planned as reused "if the stages before it write the same files again". When
it starts, every stage before it that ran in this build must have written exactly the files (SHA-256
and mode), links and deletions it wrote when it last ran for the old run (a stage the old run had
reused is compared with the run it was copied from); otherwise the stage runs. A conditional stage is
never one whose old version of a file an earlier reused stage left out (it could not run then), so a
failed condition always runs the stage normally.

## Verification

`tests/test_build_cache.py`: a code change that keeps a stage's outputs reuses every stage after it,
byte-identical to a fresh build; a change of its outputs runs them (each with its fallback reason),
also byte-identical to a fresh build; the earlier chain tests keep their results where the
condition does not apply.

## Prevention

The reuse tests above run in every gate.
