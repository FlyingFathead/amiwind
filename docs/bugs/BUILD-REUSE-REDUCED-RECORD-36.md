_Last updated with AmiWind v0.0.41-dev5 (16 October 2026)._

## Status: 10 October 2026

Fixed in v0.0.36-dev3. Hold-level builder bug (reuse); every build was held until the fix was gated.

## Symptom

The v0.0.36-dev3 build stopped one minute in, in its census stage: `intro-scene/id1/gfx/palette.lmp` did not
exist. The intro stage before it had been reused ("158 files ... every SHA-256 verified"), but its folder held 158
files where the stage writes 177.

## Where

`tools/build_cache.py`, `plan_reuse`: the record of a stage in the reuse source.

## How it happened

When a build reuses a stage, it leaves out the files a later stage, reused in the same build, replaces anyway (the
later stage brings its own version). The v0.0.36-dev2 run reused intro this way and left out 19 of its 177 files
(census, area and the stages after them replaced them), and its record of intro lists only the 158 files it copied.
The full record was kept beside it (the record-keeping repair of
[BUILD-REUSE-RECORD-RETIRED-36](BUILD-REUSE-RECORD-RETIRED-36.md)), but the reuse plan read the short one. The
v0.0.36-dev3 build reused intro from that run while census had to run again: the 19 files were nobody's, and census
found its palette missing.

## Why it was not caught

The reuse tests built chains where every later stage was reused too, or where the stage itself had really run in
the source run; no test reused a stage through a run that had itself reused it and then ran one of the stages that
had replaced its files.

## Reproduction

Always: build A; build B reusing every stage of A; change a stage that replaces files of an earlier stage and build C
reusing B. Before the repair the changed stage failed on the earlier stage's missing file.

## Repair

The reuse plan compares a stage's record in the source run with the record of the run where it really ran
(`ran_manifest`). The files missing from the short record were replaced in the source run; the stage is reused only
if every stage that touched those files (read from their full records) is reused unconditionally in this build.
Otherwise it runs again, with the reason in the reuse report. It is never reused with files missing. The full
record counts as the same outputs when every file of the short record is in it with the same SHA-256; the stage key
may differ between the two runs (a key-form change with unchanged outputs). A first version of the repair compared
the keys instead, skipped the check for intro (keys 19bb19ce and d47fb6c4) and let the resumed build fail the same way;
it was replaced before any other build.

## Verification

Regression test `test_a_reused_stage_restores_its_whole_output_when_a_later_stage_runs_again` in
`tests/test_build_cache.py` (build, reuse everything, change the stage that deletes an earlier stage's file, reuse
again: the build passes); the existing reuse-chain tests pass unchanged (every stage reused when nothing changed).
A second test covers a key change between the runs. Checked read-only on the failed runs' own records: intro's short
record (158 files) is an exact subset of the full one (177 files), 19 files left out, so the resumed build reruns it.

## Prevention

A reuse plan reads the full record of every stage; the short record only says what the source run copied.
