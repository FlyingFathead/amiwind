The 68060 is a first-class target for AmiWind's engine, next to the 68040. This page holds the plan: what is
known, the rules the work follows, and the steps. Running the game on real hardware, and the rest of the
compatibility roadmap, are in [Running AmiWind on real Amiga hardware](REAL_HARDWARE.md#compatibility-roadmap).

## What the 68060 changes

Both CPUs run the same 68k instruction set, so a game built for the 68040 runs on a 68060 unchanged, with the
CPU's support library (`68060.library`) loaded. The 68060 is the faster chip: typical Amiga cards run it at 50 to
75 MHz, some higher (our first real-hardware tester runs an A4000 with a 68060 at 82 MHz and 128 MB of Fast RAM) against 25 to 40 MHz for a 68040; it has two integer pipelines
that often issue two instructions per clock, branch prediction and caches twice as large. Quake-style software
rendering, tight integer loops with much memory access, gains a lot from that.

What the 68060 does not have in hardware, it traps to its library, which emulates the instruction in software at
a cost of many cycles each. A trapped instruction in rare code costs nothing noticeable; in per-pixel or
per-surface code it can eat a large part of the speed. A 68060 gives no 3D hardware and does not lift the AGA
chipset's memory limits either.

## What is known (17 October 2026)

> Far detail: every figure on this page before 17 October 2026 was measured with far detail **Full**
> (`aw_cull 1`, the default up to v0.0.41). From v0.0.42 the default is Strong; to compare with these
> figures, set `dbg cull 1` first ([the far test](performance/FAR-TEST.md)).

Measured on the v0.0.42 line (its engine is byte-identical to the v0.0.41 release engine). The build's FPU check
has a 68060 mode (`tools/check_fpu_unimplemented.py --cpu 68060`) that names every instruction the 68060 traps
and the engine function it sits in, and every 68040 build records them (`fpu-unimplemented-68060.json`):

- 309 `fscc` instructions (a float comparison turned into a true or false value) in 171 engine functions:
  [ENGINE-060-FSCC-41](bugs/ENGINE-060-FSCC-41.md).
- 156 64-bit `MULS.L`/`MULU.L` (GCC's way of dividing by a constant), 151 of them in 68 engine functions, and
  eight 64-bit `DIVU.L` in libgcc: [ENGINE-060-MUL64-41](bugs/ENGINE-060-MUL64-41.md). An earlier scan reported
  none; it did not recognise how this SDK's disassembler spells them.
- The 68040's own unimplemented floating-point instructions: three, in the maths library's `fmod` and `sqrt`
  error branches, on an approved list.
- No `fdbcc`, `ftrapcc`, `fmovem` with a dynamic register list or extended-precision immediates.

The experimental 68060-targeted build (`--engine-cpu 68060`, [engine profiles](ENGINE_PROFILES.md#the-68060-targeted-build))
has no `fscc` and no 64-bit multiply in engine code: what remains are six 64-bit multiplies and the eight
divides in the C library and libgcc (on its own approved list), and it converts floats to integers with
`FINTRZ`, which the 68060 runs and the 68040 traps, so it is a 68060-only binary. It builds without warnings,
is 2.6 % smaller and is built by every gate.

### Trapped instructions per frame

Counted on an emulated 68060 (below), 17 October 2026, the v0.0.41 release disks with the engine swapped,
noon, headlamp off, NPC movers off, the Balmora benchmark cameras of the
[hardware benchmark](HARDWARE-BENCHMARK.md#frame-time-in-the-game) and the Mages Guild interior (its arrival
point). Traps per frame shown, all vectors together (emulator counts: exact numbers of trapped instructions,
not times):

| Camera | 68040 build | of them in `R_RecursiveClipBPoly` / `R_EmitEdge` | of them 64-bit multiplies | 68060 build |
| --- | --- | --- | --- | --- |
| Balmora 1 | 424,064 | 301,363 / 112,111 | 1,116 | 3.6 |
| Balmora 2 | 282,443 | 188,575 / 80,634 | 1,095 | 3.2 |
| Balmora 3 | 186,895 | 141,940 / 37,800 | 219 | 3.5 |
| Balmora 4 | 238,433 | 158,986 / 68,790 | 852 | 2.5 |
| Balmora 5 | 206,378 | 153,713 / 44,086 | 261 | 1.5 |
| Mages Guild | 72,914 | 50,057 / 19,342 | 685 | 3.8 |

Eight frames per camera and run; cameras 2, 4 and 5 ran twice with the 68040 build and agree within 1 %
(camera 3 in a third run over 22 frames: 191,429).

What that costs on a real 68060 is an estimate until it is measured there. Each trap is an exception (tens of
clocks on a 68060 to enter and return) plus the library decoding the instruction and emulating it in
software; taking 200 to 500 clocks per trap, at 100 MHz:

| Camera | Traps per frame (measured) | Time at 100 MHz (estimated) | Share of a 5 s frame (estimated) |
| --- | --- | --- | --- |
| Balmora 1 | 424,064 | 0.85 to 2.1 s | 17 to 42 % |
| Balmora 2 | 282,443 | 0.56 to 1.4 s | 11 to 28 % |
| Balmora 3 | 186,895 | 0.37 to 0.93 s | 7 to 19 % |
| Balmora 4 | 238,433 | 0.48 to 1.2 s | 10 to 24 % |
| Balmora 5 | 206,378 | 0.41 to 1.0 s | 8 to 21 % |
| Mages Guild | 72,914 | 0.15 to 0.36 s | 3 to 7 % |

The 5 s frame is the one real-hardware figure so far (a 68060 at 100 MHz, about 0.2 frames per second, an
earlier build: [real hardware](REAL_HARDWARE.md)); it was not taken at these cameras. The real cost per trap
comes from running `awtraps` (below) and both engines at one pose on a real 68060.

With the 68040 build on a 68060 almost every trap is an `fscc` in two renderer functions: the brush-model
clipping (`R_RecursiveClipBPoly`, two `fscc` per BSP node visited) and edge emission (`R_EmitEdge`), the code that
already takes most of a slow frame ([CHIM-SLOWCPU-FRAMETIME-33](bugs/CHIM-SLOWCPU-FRAMETIME-33.md)). Each one
runs the 68060.library's software emulation. The 64-bit multiplies add hundreds per frame (`R_RotateBmodel`,
the sky). The 68060 build's few traps per frame are the C library's `rand`.

The same disks played on the emulated 68060 with the 68060 build (Balmora, the Mages Guild), so the build runs.

### On a 68040

The same count on an emulated 68040 (FS-UAE `cpu = 68040`, JIT off, unimplemented instructions trapping, the
system's `68040.library`), the same disks, cameras and settings, the 68040 engine: zero traps, at every camera, in
the Mages Guild and during the boot (measured 17 October 2026). The three approved `FMOVECR` error branches in
`fmod` and `sqrt` never ran. The counter does catch 68040 traps: a test program's 1,000 `FINTRZ` and 1,000
`FMOVECR` counted 2,000. What this emulator cannot show are traps that depend on the data: a real 68040 also
traps on denormalized (very small) floating-point operands, which FS-UAE computes without a trap (the test
program's 1,000 denormal loads counted none), so whether the game meets such numbers is still open.

### Counting trapped instructions

`engine/aga/bench/awtraps.asm` (`make traps` in `engine/aga`) is a small measurement program, never on a game
disk. Run after the CPU library has installed its handlers, it puts a counting step in front of the exception
vectors the library uses (11: unimplemented floating-point instructions, which on a 68060 include `fscc`;
55: unimplemented data type; 60: unimplemented effective address; 61: unimplemented integer instructions), each
passing on to the library's handler, counts the frames the engine shows (intuition's `ChangeScreenBuffer`)
and keeps a table of the trapping addresses. `awtraps watch FILE` writes the counters every second; traps per
frame are the difference of two snapshots. The addresses map to engine functions through the link map. The
emulator has to trap like the chip: FS-UAE with the JIT off and `uae_cpu_no_unimplemented = true`,
`uae_fpu_no_unimplemented = true`.

The boot disk also needs the system's own `SetPatch` before the CPU library: the MMULib `68060.library` stops
the boot with an alert without it ([FPU-SUPPORT-MMULIB-SETPATCH-41](bugs/FPU-SUPPORT-MMULIB-SETPATCH-41.md)).

### Both engines on the game disk

From v0.0.42 every 68040 engine build also builds the 68060 engine of the same profile (`AmiWind060`), and the
game disk carries both, with a small program, `AmiWindCPU` (`engine/aga/boot/cpusel.asm`), that the startup
sequence runs first:

```
FailAt 10
SYS:C/SetPatch QUIET        (when the build was given SetPatch with --amiga-libs)
SYS:AmiWindFPU              (when the build was given a CPU library)
SYS:AmiWindCPU
If WARN
  SYS:AmiWindCheck
  Stack 300000
  SYS:AmiWind060
Else
  SYS:AmiWindCheck
  Stack 300000
  SYS:AmiWind
EndIf
```

`AmiWindCPU` finds a 68060 as `AmiWindFPU` does (the 68060 flag, or on Kickstart 3.1 the 68060-only PCR
register), prints which engine it picked and returns WARN on a 68060. The 68040 build stays the default for
every other CPU. A file `S:AmiWind-68040` on the boot partition makes a 68060 start the 68040 build too, to
compare both on the same machine. On a 68060 without a running `68060.library` it prints a notice between
dashed lines and counts down 10 seconds (S stops the countdown, Return then goes on); the boot check after it
stops the game there, as before ([BOOT-68060-FPU-FAIL-32](bugs/BOOT-68060-FPU-FAIL-32.md)).
Checked 17 October 2026 on an emulated 68060 with the v0.0.41 disks and both engines: with the library the
68060 build starts and reaches the main menu; without it the notice and the countdown come first; on a 68040
the 68040 build starts.

The two engines draw the same picture as far as measured: at Balmora camera 3 the 68040 and 68060 builds give
identical frames. At the other cameras and in the Mages Guild the frames differ only in animated things (a
distant figure, a candle flame, people idling) that also differ between two runs of the 68040 build; no
geometry, edge or texture difference showed. That is not yet a strict proof: animation runs on game time, and
a comparison with a frozen animation clock is still to do. Both builds truncate floats to integers the same
way (the 68040 build sets the rounding mode and uses `FMOVE`, the 68060 build uses `FINTRZ`) and keep the same
order of floating-point operations (no fast-math), so no rounding difference is expected.

## Emulating a 68060 machine

Checked 16 October 2026: can FS-UAE and WinUAE stand in for our tester's machine (an A4000, a 68060 at 82 MHz,
128 MB of Fast RAM, Kickstart 3.1)?

What matches exactly. FS-UAE 3.1.66 (our headless emulator, in Docker) accepted and ran this setup; its log
confirmed every setting:

```
amiga_model = A4000/040
kickstart_file = <your Kickstart 3.1 A4000 ROM>
cpu = 68060
fpu = 68060
chip_memory = 2048
zorro_iii_memory = 131072
fast_memory = 0
```

The log line `CPU=68060, FPU=68060, MMU=68060` and a Zorro III memory size of 128 MB. That covers the CPU model with
its FPU and MMU, the AGA chipset of the A4000, 2 MB of Chip RAM, 128 MB of Fast RAM (Zorro III, up to 1 GB is
possible) and Kickstart 3.1. WinUAE offers the same choices (68060 with its internal FPU and MMU, the A4000, Zorro III
Fast RAM). The accelerator card itself is not emulated as a board, and does not need to be for the game: what matters
is the CPU, the memory and the 68060.library, which the game loads at boot as on the real machine.

What does not match: the clock. Neither emulator times a 68060 cycle by cycle (two pipelines, branch prediction,
caches). FS-UAE's cycle-exact mode with a CPU multiplier (clock = multiplier x 3.546895 MHz) gives a fixed pace of
emulated cycles per instruction, the same for a 68040 and a 68060. Measured 16 and 17 October 2026 with timed
integer and divide loops (FS-UAE 3.1.66, Kickstart 3.1, caches on): with `cpu = 68060-NOMMU` (or
`68040-NOMMU`) the multiplier sets that pace (multiplier 23 ran the loops 3.3 times faster than 7); with
`cpu = 68060` or `68040` (the models with an MMU) FS-UAE accepts and logs the multiplier, and also
`uae_cpu_frequency = 82000000`, but ignores them: x7, x14 and x23 took the same 42 seconds for 20 million
iterations, about 30 times slower than the -NOMMU model at x7. So a "68060 at 82 MHz" preset is the -NOMMU model
at multiplier 23: an 81.6 MHz pace of a 68040-like CPU, not a 68060's timing. Without the cycle-exact mode ("as
fast as the host can", JIT off) the same loop took 1.1 to 1.3 seconds. So "a 68060 at 80 MHz" can only be approximated:
run the same benchmark (the [hardware benchmark](HARDWARE-BENCHMARK.md) program and the benchmark cameras) on the
real machine and in the emulator, then turn the emulator's speed setting until the numbers match, and record that
setting in the preset with the real machine's numbers next to it. Emulator figures stay relative until checked
against the real machine.

What the emulator does give a 68060 build. The instructions a 68060 does not run in hardware (the `fscc` and the
rest, see above) can be made to trap as on the real chip when the JIT compiler is off: slow, but it counts every
trapped instruction, which is exactly the measurement the 68060 steps below need.

## The rules

1. The 68040 build stays the baseline: it is never broken or replaced, and every release runs on it.
2. One game for both CPUs: the engine detects the CPU at start-up and picks its 68040 or 68060 version of each
   hot routine; the 68060 code path avoids the instructions the 68060 traps.
3. Algorithm first: change what the renderer does before making it faster. Removing work beats optimising it.
4. Our own assembly only for measured bottlenecks of our frame, written from our C code; no wholesale import of
   other engines' assembly (upstream AmiQuake's assembly was measured: no gain on our hot path), and never a whole
   renderer in assembly.
5. Every 68060 path draws exactly the same picture as the 68040 path at the same camera poses (pixel-identical
   tests), and plays the same.
6. Every gain is measured at identical poses: C at different optimisation levels, 68060-targeted C, and selected
   assembly; no speed-up is claimed before it is measured, first in the emulator, then on a real 68060.

## Order of work, by measured cost

From the measured frame of a slow 68040 ([CHIM-SLOWCPU-FRAMETIME-33](bugs/CHIM-SLOWCPU-FRAMETIME-33.md)):

1. Brush-model clipping (`R_RecursiveClipBPoly`), 65 to 72 % of the 3D time: first an algorithm that visits fewer
   BSP nodes and transforms fewer planes, assembly only after that.
2. Fog drawing and the day-night sky.
3. Edge scanning and span drawing.
4. Float-to-integer conversion and edge emission: fewer FPU control-register changes in hot loops.

## Steps

- [x] The build's FPU check gets a 68060 mode: the 68060's extra traps (`fdbcc`, `fscc`, `ftrapcc`, `fmovem` with
  a dynamic register list), reported per engine function through the link map, as for the 68040. Done 16 October
  2026, with the 68060's integer traps (64-bit multiply and divide, `movep`, `chk2`, `cmp2`, `cas2`) too.
- [x] A 68060-targeted engine build (`-m68060`), measured: which traps it avoids (16 October 2026: every `fscc`
  and every 64-bit multiply in engine code; see above). How fast it runs: on a real 68060, still to measure.
- [x] An emulated 68060 run at the benchmark poses counting trapped instructions per frame (17 October 2026,
  see [Trapped instructions per frame](#trapped-instructions-per-frame)).
- [x] Start-up CPU detection: two binaries for now (17 October 2026, [both engines](#both-engines-on-the-game-disk)).
- [ ] Per-CPU hot routines in one game binary.
- [ ] The CPU support library set when building (an `amiga-libs` folder next to `Data Files`) or dropped onto the
  game disk later; a boot notice, set apart by dashed lines, when a 68060 is found without its library (a
  countdown; S stops it).
- [x] 68060 emulator presets next to the 68040 ones, for FS-UAE and WinUAE ([emulator presets](chim/build_guide/EMULATOR_PRESETS.md)):
  the launcher lets the player pick 68040 or 68060, with a quick choice of ready-made setups (for example a
  68060 at about 80 MHz with 128 MB of Fast RAM, like our tester's A4000), so the game can be playtested in the
  emulator on the same kind of machine it will run on.
  The CPU, memory and Kickstart match exactly; the speed is calibrated against the tester's benchmark numbers
  (see [Emulating a 68060 machine](#emulating-a-68060-machine)).
- [ ] A real 68060 baseline first (the benchmark run on a 70 to 82 MHz card), then each step measured against it.
